# Rule catalog

All rules validate through Pydantic with unknown fields rejected. SQL identifiers are bounded alphanumeric/underscore names. SQLAlchemy reflects approved objects and constructs expressions; values are bound parameters. Each result stores ID, name, table, kind, UTC timestamp, status, measured value, expected configuration, affected count where meaningful, details, and duration.

| Kind | Measurement and behavior |
|---|---|
| null | Count NULLs in required column; fail above tolerance |
| duplicate | Excess rows beyond one per key; NULL forms a group; configure null check separately |
| reference | Count non-NULL child keys without a parent; NULL checked separately |
| row_count | Inclusive minimum/maximum total rows |
| freshness | Hours since maximum timestamp; empty/all-NULL and timestamps over six minutes in future fail |
| numeric_range | Rows outside inclusive bounds, including NULL |
| schema | Added, missing, changed type-family/nullability columns versus explicit baseline |
| reconciliation | Absolute difference of aggregate sums; tolerance configurable |
| business_rule | Count rows violating column le/ge/eq other_column, including NULL |
| anomaly | Absolute percentage row-count change against last completed non-failing baseline; first run warns; zero to nonzero measures 100% |

Severity is warning or failure. Execution exceptions are error and produce a sanitized operator hint. There is no pass-on-error behavior. Rule sets allow 1–100 unique IDs. Threshold changes are reviewed file changes, never LLM decisions.

Example:
```json
{"id":"required_customer","name":"Customer name required","table":"Customers","schema_name":"dbo","kind":"null","column":"CustomerName","tolerance":0,"severity":"failure"}
```

The checked-in Northstar catalog uses verified columns but proposed business thresholds. Keep configuration versioned alongside deployment commits. Demo rules are generated by `dqagent.demo.rules()` and use the identical validated contract and engine.
