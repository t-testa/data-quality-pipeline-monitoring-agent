# Security model

## Trust boundaries

Source contents, operator questions, and external logs are untrusted. Only deterministic aggregate results enter diagnostics. The model receives numeric/status evidence and IDs, never database row text, error messages, credentials, names, or connection strings. Its structured output contains only evidence IDs and predefined guidance categories. Server validation checks both existence and applicability. Confirmed facts are copied from storage, not generated by the model. Invalid output and provider failure fall back to deterministic evidence. This limits explanatory flexibility but makes grounding auditable.

The user-facing investigation includes passing and non-passing checks. The model context remains a separate projection containing only the run summary and non-passing checks. Applicable numeric thresholds and numeric baseline/reconciliation details are explicitly allowlisted; booleans, nonfinite numbers, arbitrary strings and nested values are rejected from numeric fields. Business-rule operators are limited to `le`, `ge` and `eq`. Missing numeric values remain null. Complete evidence records and raw expected/details dictionaries are never forwarded to the provider. The existing bounded evidence retrieval, authorization, request budget and citation validation remain in force.

The source integration accepts only explicit encrypted `mssql+pyodbc` URLs with certificate validation. Opaque `odbc_connect`, duplicate or compound options, invalid option keys and `TrustServerCertificate=yes` are rejected. Source commands are generated SELECTs. Both the CLI and source verification script reject sysadmin/db_owner/db_ddladmin and INSERT/UPDATE/DELETE/ALTER/CONTROL/TAKE OWNERSHIP on monitored objects; SELECT is required. Database-enforced grants remain authoritative. A DBA must provision and verify a dedicated identity, including grants outside the monitored objects and procedure/impersonation permissions. The old integrated-admin discovery shortcut has been removed; the script now uses the approved `DQ_SOURCE_URL` and the same least-privilege gate. No live source connection was made during hardening.

## Authentication and authorization

Two distinct random bearer secrets, each at least 32 characters, are required before API startup. The read token can inspect evidence and request deterministic diagnostics. The diagnostic token may also trigger optional paid OpenAI requests. Both roles see all monitoring data in this single-workspace application; there is no multi-tenant isolation. Tokens are compared in constant time and never stored by the browser. Restart with new environment secrets to rotate them.

Public routes contain only static dashboard assets and minimal liveness/readiness responses. Readiness verifies metadata access without returning records or error details. Every monitoring endpoint, schema endpoint and tool call requires a token. No permissive CORS is enabled. Browser rendering uses textContent, never source-data HTML. Content Security Policy blocks third-party scripts and framing. HTTP is permitted only on loopback or inside an encrypted SSH tunnel. The Azure design publishes no application port on the VNet and uses SSH keys plus an approved private access route.

MCP is stdio-only and proxies authenticated requests to FastAPI. It has no direct source or metadata access and does not start an HTTP server. The OS account and client configuration must be trusted. Use the read token for MCP. Remote API URLs must use HTTPS; HTTP is limited to localhost. Redirects and environment proxy inheritance are disabled.

## Operational limits

- 8 KiB HTTP request bodies, including chunked requests, with a ten-second receive deadline; strict typed inputs and 1,000-character questions.
- 120 authenticated requests/minute per role in one API process; one worker is required.
- 20 attempted AI requests/day, persisted atomically in SQLite; one provider call, no SDK retries, 20-second network-operation timeout, 600 output tokens. Question plus projected evidence is limited to 16 KiB; larger contexts retain deterministic facts and skip AI. This is not an exact token or dollar cap; the system instruction and output schema also consume input tokens. A slowly streaming provider response is not subject to a separate absolute wall-clock deadline.
- The provider destination is pinned to `https://api.openai.com/v1`; ambient base URLs/proxies and redirects cannot reroute requests. Known configured secrets and recognizable credential patterns are redacted from questions. This is not general PII/DLP detection: operators must not submit private row text in questions. SDK/HTTP transport logs are disabled to prevent request-body logging.
- MCP/evidence: up to 100 results and 256 KiB. Queries have five-second connection and ten-second statement timeouts; two SQL connections maximum.
- No arbitrary SQL, uploads, shell tools, mutation API, remote incident-generation endpoint or autonomous remediation.
- Raw SQL/provider exception text is not stored or returned. Raw access logs remain disabled. Bounded structured request events contain a generated request ID, fixed route template, status and duration, with no body, headers or URL values. Successful/error HTTP responses normally include `X-Request-ID`; unexpected unhandled 500s are still correlated internally by the generated event. Run/check IDs remain the evidence correlation keys.
- AI rejection events/API metadata contain only allowlisted reasons and bounded reference profiles. Missing/empty lists, schema errors, unknown references, unsupported guidance, provider failures and unexpected local validation failures remain distinct. Arbitrary rejected reference strings are never logged: known references use supplied-context indices; unknown strings use capped lengths/format classes and a truncated HMAC fingerprint with an ephemeral process-local key. No prompt, raw model output, nested content, headers, exception text or full validation-error payload is retained. SDK errors that do not expose a complete reference field are explicitly marked unavailable. This metadata explains rejection without relaxing exact scope/category validation.
- `.env`, databases, backups, artifacts and local test data are ignored by Git and excluded from Docker context. Protect the workspace and `.env` with OS ACLs; local administrator access is trusted.
- Container runs as UID 10001, has a read-only root filesystem, no Linux capabilities, no setuid/setgid helpers under /usr and a named local volume. Removing privilege bits is a compensating control, not an OS vulnerability fix.
- Readiness checks metadata accessibility and a configurable free-space floor (default `DQ_MIN_FREE_DISK_BYTES=67108864`). It is not a write/durability proof. Backups use exclusive private file creation, integrity verification and removal of only newly created partial output on failure; Windows directory ACLs and encrypted off-host storage remain operator responsibilities.

## Remaining hardening

This is a private, single-operator service, not a public SaaS. Before wider organizational use: add individual Entra identities and audit trails, centrally managed secret rotation, authenticated TLS termination, retention/alert delivery, a server database, bounded multi-tenant authorization and scheduled dependency updates. Image scanning is now performed locally and configured in CI; remaining OS advisories require documented applicability review before production. The CI image gate rejects fixable high/critical findings; it does not certify unfixed findings as safe. No automatic recovery is attempted if a process dies during a pipeline; use explicit operator recovery. Keep backups on an encrypted private destination and test restoration.

The runtime base is pinned by digest, uses Debian 13 security updates and excludes pip/ensurepip after hash-verified dependency installation. Test dependencies are installed only in the separate test image. A pinned base does not freeze apt repositories or vulnerability databases; rescan every final image and retain its identity. Model prioritization never removes persisted findings from a diagnostic response.
